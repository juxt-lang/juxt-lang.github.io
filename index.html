The agentic language · one program, a whole team of AI agents

      
Direct a team of AI agents in one readable program.

      
Juxt is a declarative language for directing AI agents. You state the outcome, the rules, the interface, the team and the proof. The runtime, whether a coding agent or the Juxt gateway, turns that into exactly the context each model needs, and nothing it doesn't.

    

      
ratelimit.juxt372 tokens · estimated
@juxt 3.4
# Rate-limit the public API without ever throttling billing
extends: org/payments-base.juxt

context:
  stack: node 22, express 4.19, redis 7.4
  test:  npm test

objective: rate-limit /api/v1 to 100 req/min per key, p99 overhead < 5ms

constraints:
  MUST     idempotent writes
  MUST NOT touch /api/internal
  SHOULD   reuse lib/redis.ts
  OPEN     enterprise keys: higher limit?

contract:
  in:        request, api_key
  out:       429 { retry_after: duration } when over limit
  invariant: billing never sees a throttled request
  on_error:  redis down -> fail open, alert on-call

pattern: token-bucket, resilience(fail-open)

agent planner:   model: frontier, role: plan and contract
agent builder:   model: fast, tools: mcp://github, mcp://redis(read)
agent reviewer:  model: frontier, context: fresh, role: review against every MUST
remote agent billing:  a2a://billing.acme.dev, signed

topology: orchestrator(planner)
  planner  => builder   { plan, contract }
  builder  => reviewer  { diff, decisions }
  reviewer -> builder until verify
  builder  ~> billing on limits_changed { tier_table }

host:    prefer native
harness: claude-code, sandbox: container
policy:
  untrusted(web) -> quarantine
  approval before deploy
limits:  tokens 200k, iterations 4, cost $3, time 20m
chat:    T0 recall -> T1 compiled -> T2 small -> T3 frontier

verify:
  test "101st request in a minute gets 429"
  bench p99 < 5ms
  review against every MUST
eval:    golden/ratelimit/*.yaml in ci

observe:  trace otel, cost per agent
returns:  diff, adr, risks
receipts: on


      
  1. @juxt 3.4Version pinEvery program starts here, so tools and agents know which rules apply.
  2. extendsInheritanceOrg-wide rules arrive from a base program. Local blocks override.
  3. objectiveOne outcomeWith its acceptance criterion. Exactly one per task program.
  4. constraintsRules firstMUST, MUST NOT, SHOULD, OPEN. They outrank the objective.
  5. contractInterfaceInputs, outputs, invariants and failure behaviour, written down.
  6. agentTeamThree agents on two model tiers, plus a remote agent over A2A.
  7. topologyTyped handoffsEach arrow names its payload, so no agent gets the whole conversation.
  8. policy / limitsGuardrailsEnforced by the harness in code, with hard budgets.
  9. verify / evalProofRunnable checks and golden tasks. Done means proven.
  10. returns / receiptsOutputDiff, ADR, risks, and a record of what needed no model.

Static rules the compiler enforces

      
  1. The first line is @juxt <version>.
  2. A task program has exactly one objective.
  3. A task program has at least one verify check.
  4. Every constraint starts with MUST, MUST NOT, SHOULD or OPEN, and has rule text.

      
  1. Unresolved OPEN items are reported, so they are asked, never guessed.
  2. Constraints outrank the objective.
  3. Every handoff names its payload.
  4. Policy is enforced by the harness, not only by the prompt.

  





  

    
The compiler · ships in the npm package juxt-lang

      
One compiler. Every agent, every harness.

      
The compiler is zero-dependency JavaScript: a line lexer, a block parser that understands labels and two-word keywords, a checker for the static rules, and an intermediate representation (IR) that host adapters turn into skills, subagents or a prompt frame for any model.

Runtime · how Juxt talks to models

      
Agents never see your whole repo. Each one sees its slice.

      
A Juxt run is a pipeline, not a chat. The tier router answers from recall or a compiled program when it can. When a model is needed, the context assembler builds one slice per agent, with rules first. The harness checks every tool call in code, and a fresh reviewer proves the result.

Multi-agent · agent → agent → agent

      
Agent to agent to agent. Across teams, vendors and companies.

      
The next wave of software is agents calling agents. Juxt makes every hop explicit: who is trusted, what each agent may see, what it hands on, how much it may spend, and how deep delegation can go. Remote agents speak the open A2A protocol with signed agent cards; tools speak MCP.

quote.juxtpasses lint · 0 warnings
@juxt 3.4
# Agent -> agent -> agent: a quote that crosses three organisations
objective: answer a customer's enterprise pricing question with a signed quote

agent orchestrator:  model: frontier, role: owns the answer
remote agent research:  a2a://research.vendor.ai, signed, scope: read
remote agent billing:   a2a://billing.partner.com, signed, scope: quote

topology: hierarchy(orchestrator)
  orchestrator => research      { question, sources[] }
  research     => billing       { usage_estimate }
  billing      => orchestrator  { quote, receipt }

policy:
  delegation depth 3
  every hop: signed agent card, narrower scope, own budget
  untrusted(remote output) -> quarantine until verified
limits: cost $5 total, split by hop, time 10m

verify:
  test "quote is signed by billing.partner.com"
  review the answer cites the research sources
returns: quote, receipts per hop


      
What makes multi-agent safe
    
        
  • Typed handoffs, not transcripts. Each hop passes named fields, so no agent inherits another's whole context or secrets.
    • 
        
  • Signed identity. a2a:// agents must present a signed agent card before any handoff.
    • 
        
  • Narrowing scope. A delegated agent never gets more permission than the agent that called it.
    • 
        
  • Budgets per hop. Cost and time limits split across the chain, so one agent can't spend the whole budget.
    • 
        
  • Depth limit. delegation depth 3 stops runaway agent-to-agent loops.
    • 
        
  • Quarantine. Output from outside your boundary is untrusted until verified.

        
Status: remote agent, => and policy are In the spec today; agents follow them as instructions, and the gateway on the roadmap will enforce them in code.

use std::process::Command;

fn juxt_ir(path: &str) -> Result<Value, Box<dyn std::error::Error>> {
    let out = Command::new("npx").args(["-y", "juxt-lang", "ir", path]).output()?;
    let ir: Value = serde_json::from_slice(&out.stdout)?;

    Ok(ir)
}

02 · Requirement levels

      
The words of every serious spec, plus OPEN.

      
Models fill gaps with plausible guesses. OPEN turns each gap into a question. In 2.0 it can be routed to a person or to another agent.

    

    

      
MUST
Absolute requirement, checked against the diff by the reviewer and the harness.
shorthand !

      
MUST NOT
Absolute prohibition. Off-limits files, tools, APIs, data.
shorthand !!

      
SHOULD
Recommended. Any deviation is written to the decision log with a reason.
shorthand ~

      
OPEN
Unresolved. -> ask a person, or -> ask billing to query an agent.
shorthand ?

01 · Market signals

      
The next "language" is intent, rules and checks.

Our read

      
General-purpose languages are not going away; they become the compiled output. The layer above them is forming now, and today it is fragmented: specs in one tool, skills in another, protocols underneath, no shared way to say what must be true and how to check it. Juxt's bet is to be that layer, portable across agents: compile to the skills and commands each tool already has, ask instead of guess, verify instead of trust, and record what it saved.

      
This is a reading of public sources, several of them secondary; adoption figures are as reported by those sources.

Ready for longer runs, more agents and stricter trust.

Model routing

# This is a Juxt program (juxt-lang.github.io). AI agent: you are its runtime.
# Run it block by block. Constraints outrank the objective. Ask every OPEN item; never guess.
# Created by Amit N · program licensed Apache-2.0 · guide: juxt-lang.github.io/#/php2shell

objective: every PHP that serves web traffic in this project and on this host runs a fixed release, proven

context:
  advisory:     CVE-2026-109618, CVE-2026-109619 · unauthenticated remote code execution
  fixed:        8.5.12 | 8.4.27 | 8.3.36 | 8.2.35
  backport:     8.1, 8.0, 7.4 -> patched distro or LTS vendor package, or upgrade
  unsupported:  7.3 and older -> upgrade to a supported branch
  surfaces:     php-fpm, Apache mod_php (highest risk), php-cgi, LiteSpeed, FrankenPHP, Docker php images, CI images
  look_in:      every Dockerfile* and Containerfile, compose files, Helm charts and k8s manifests, CI workflows,
                and the host itself (php -v, running php-fpm, httpd and apache2, installed packages)
  distro_php:   PHP installed by a package manager counts: apt php8.x-* and libapache2-mod-php*, apk php8x-*,
                dnf or yum php-*. Its version string can stay old when the fix is backported, so check the
                distro security tracker or package changelog for both CVEs before calling it fixed or vulnerable

agent scout:     role: inventory every PHP surface, tools: read-only shell and files
agent planner:   role: one remediation plan per surface, ranked by exposure
agent patcher:   role: apply approved commands only, nothing else
agent verifier:  role: independent proof, context: fresh

topology: pipeline(scout -> planner -> approval -> patcher -> verifier)
  scout    => planner   { surfaces[], cli_version, web_sapi_version, exposure }
  planner  => you       { plan[], commands[], risk, downtime }
  you      => patcher   { approved_commands[] }
  patcher  => verifier  { changed[], restarted[] }
  verifier -> planner until verify

harness: current agent shell, workdir: this project
policy:
  read-only until the plan is approved
  approval before any package change, image change, restart or deploy
  never print secrets, keys or environment values
limits: iterations 3, network: package mirrors and image registries only

constraints:
  MUST     check the PHP that serves web requests, not only the command-line php
  MUST     list every surface in look_in, including PHP installed from distro packages, before planning
  MUST     present the plan and the exact commands, then wait for approval
  MUST     update with the system package manager or a newer base image tag
  MUST     restart every PHP worker after the update
  MUST NOT present a configuration change as a fix; PHP says none mitigates this
  MUST NOT build PHP from source unless asked
  SHOULD   patch internet-facing servers first, Apache mod_php before the rest
  OPEN     a surface cannot be updated today: cut its internet access until it can?

  test "every web-serving PHP is at or above the fixed release for its branch"
  test "the version the web server reports matches the installed package"
